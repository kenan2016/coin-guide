这是一个非常高阶的问题！

在中心化交易所（CEX）中，**“接入合约”通常指的不是区块链上的智能合约（Smart Contract，如 Solidity），而是“永续合约交易” (Perpetual Futures Trading)**。

这是一套完全独立的业务体系。如果说现货交易（Spot）是“一手交钱一手交货”，那么合约交易就是**“交保证金对赌”**。

接入合约交易，你的系统复杂度会指数级上升。最核心的挑战在于：**杠杆 (Leverage)** 和 **爆仓 (Liquidation)**。

以下是基于我们现有架构的 **合约交易接入指南**。

---

### 1. 架构调整：双核心模式

你不能把合约逻辑塞进现有的 `TradeService` 里。合约和现货必须物理隔离。

* **现货引擎 (Spot Engine)**: 处理 `BTC/USDT`。逻辑：冻结余额 -> 交换资产。
* **合约引擎 (Futures Engine)**: 处理 `BTCUSDT_PERP`。逻辑：冻结保证金 -> **开仓/平仓**。
* **风险引擎 (Risk Engine)**: **新增组件**。它是一只“盯着所有人的眼睛”，一旦有人亏损超过保证金，立即触发强平。

---

### 2. 数据库设计 (新增核心表)

合约交易不再只是操作 `Wallet` 表，而是操作 **`Position` (仓位)** 表。

#### A. 仓位表 (Position)

记录用户持有了多少合约，开了几倍杠杆。

```sql
CREATE TABLE `contract_position` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `user_id` bigint NOT NULL,
  `symbol` varchar(20) NOT NULL,    -- BTCUSDT
  `direction` varchar(10) NOT NULL, -- LONG(做多) 或 SHORT(做空)
  
  `leverage` decimal(10,2) NOT NULL, -- 杠杆倍数 (例如 10x, 100x)
  `size` decimal(36,18) NOT NULL,    -- 持仓数量 (单位: 张 或 BTC)
  `entry_price` decimal(36,18) NOT NULL, -- 开仓均价
  `margin` decimal(36,18) NOT NULL,  -- 当前持有的保证金 (USDT)
  `liquidation_price` decimal(36,18) NOT NULL, -- 强平价格 (算出来的)
  
  `unrealized_pnl` decimal(36,18) DEFAULT 0, -- 未实现盈亏 (浮动盈亏)
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_symbol` (`user_id`, `symbol`) -- 全仓模式下通常单币种单向持仓
);

```

#### B. 合约账户 (Contract Wallet)

现货账户和合约账户通常是隔离的（避免现货里的钱被合约爆仓亏光）。需新增一张表或在 Wallet 表加字段区分 `type=SPOT/FUTURE`。

---

### 3. 核心逻辑一：开仓 (Open Position)

**场景**：用户有 1000 USDT，开 **10倍杠杆 做多** BTC。当前 BTC 价格 50,000。

**后端逻辑 (`ContractService`)**：

1. **计算保证金**：
   用户想买 1 BTC（价值 50,000 USDT）。
   因为 10倍杠杆，用户只需要出  USDT。
   *等等，用户只有 1000 U，所以他只能买 0.2 BTC。*
   需冻结保证金： USDT。
2. **下单逻辑**：
   和现货一样，生成订单 `OrderEnt`，推送到内存撮合引擎。
3. **成交回调 (关键)**：
   撮合成功后，**不是交换资产**，而是 **创建/更新仓位**。
* **INSERT/UPDATE Position**:
* `size` += 0.2 BTC
* `margin` += 1000 USDT
* `entry_price` = (旧持仓 * 旧均价 + 新成交 * 新价格) / 总持仓





---

### 4. 核心逻辑二：强平/爆仓 (Liquidation) —— 最难的部分

这是合约系统的**死神**。

你需要写一个独立的**风险引擎 (Risk Engine)**，它是一个死循环的高性能服务。

**工作流程**：

1. **监听价格 (Mark Price)**：
   从 Redis 实时获取最新的 BTC 价格（标记价格，防止插针）。
2. **扫描所有仓位**：
   遍历 `contract_position` 表里所有的活跃持仓。
3. **计算亏损**：
* `做多浮动盈亏 = (当前价 - 开仓价) * 持仓数量`
* `做空浮动盈亏 = (开仓价 - 当前价) * 持仓数量`


4. **判断爆仓**：
   如果 `保证金 + 浮动盈亏 <= 维持保证金(Maintenance Margin)`。
   说明钱亏光了！
5. **执行强平**：
* **接管**：系统自动生成一笔 **市价平仓单**，不经过用户同意，直接扔进撮合引擎。
* **清算**：仓位归零，剩余的一点点渣（如果有）注入**风险准备金 (Insurance Fund)**。



**Java 伪代码 (RiskEngine.java)**:

```java
@Scheduled(fixedRate = 100) // 100毫秒扫一次，极其高频
public void checkLiquidation() {
    BigDecimal currentPrice = redisTemplate.get("price:BTCUSDT");

    List<Position> positions = positionMapper.selectAllActive();
    
    for (Position pos : positions) {
        BigDecimal pnl = calculatePnL(pos, currentPrice); // 算盈亏
        BigDecimal remainingMargin = pos.getMargin().add(pnl); // 剩余保证金
        
        // 维持保证金率 (比如 0.5%)
        BigDecimal maintenanceMargin = pos.getValue().multiply(0.005); 

        if (remainingMargin.compareTo(maintenanceMargin) < 0) {
            // 🔥 触发强平！！！
            executeForceClose(pos);
        }
    }
}

```

---

### 5. 核心逻辑三：资金费率 (Funding Rate)

**场景**：为什么永续合约的价格（50,005）和现货价格（50,000）几乎一样？因为有资金费率。

* **逻辑**：每 8 小时执行一次。
* **如果 合约价 > 现货价**：做多的人 给 做空的人 付钱（鼓励做空，把价格打下来）。
* **如果 合约价 < 现货价**：做空的人 给 做多的人 付钱。

**实现**：一个定时任务，遍历所有持仓，直接在用户的 `margin` 字段上加减金额。

---

### 6. 总结：接入合约的代价

如果你决定接入合约，你的项目将不再是一个“简易交易所”，而是一个**金融衍生品交易系统**。

**你需要增加的代码量：**

1. **ContractMatchEngine**: 一套新的撮合引擎（逻辑几乎一样，但处理的对象是合约订单）。
2. **RiskEngine**: **全新**，最复杂，必须极其精准，否则交易所会亏穿。
3. **ContractService**: 处理开仓、平仓、调整杠杆、追加保证金。
4. **行情源**: 必须引入**标记价格**（通常是多家交易所现货价格的加权平均），防止被自家用户恶意操控价格导致连环爆仓。

**建议**：
作为学习项目，目前的现货系统已经足够复杂。如果非要挑战合约，建议先实现 **“独立的风险扫描线程”**，这是合约交易的灵魂。
