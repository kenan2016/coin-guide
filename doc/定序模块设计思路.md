**定序网关 (Sequencing Gateway)** 是高性能交易所架构中**最硬核**的组件之一。

它的存在只有一个目的：**确保确定性 (Determinism)**。

### 为什么需要定序？

在分布式系统中，如果此时此刻有两个撮合引擎（主机 A 和备机 B）同时在运行（为了高可用）：

1. 用户 X 下单买入。
2. 用户 Y 下单卖出。

如果不定序，可能发生：

* **主机 A** 先收到了 X，再收到 Y -> 成交了。
* **备机 B** 先收到了 Y，再收到 X -> 没成交（因为价格变了）。

**结果**：主备数据不一致，备机无法接管主机。

**定序网关的作用**：给进入系统的每一个请求打上一个**全局唯一、连续递增的序号 (Sequence ID)**。无论你有多少个下游引擎，只要它们按这个序号处理，最终的状态就**绝对一致**。

---

### 1. 架构位置

定序网关位于 **API Gateway** 和 **撮合引擎** 之间。

* **输入**：来自 API 的并发 HTTP/WebSocket 请求。
* **处理**：排队 -> 打上 ID (1001, 1002, 1003...) -> 持久化日志。
* **输出**：将带有 ID 的事件同时广播给 **主机引擎** 和 **备机引擎**。

---

### 2. 实现方案 A：基于 Redis (MVP / 学习版)

这是最容易实现的方案，适合你的学习项目，甚至可以支撑中小型业务。

**原理**：利用 Redis 的 `INCR` 原子操作生成 ID。

#### 代码实现

**SequencerService.java**

```java
@Service
public class SequencerService {

    @Autowired
    private StringRedisTemplate redisTemplate;
    
    // 专门用来计数的 Key
    private static final String SEQ_KEY = "global:order:sequence";

    /**
     * 为订单申请全局唯一序号
     */
    public long nextId() {
        // Redis INCR 是原子性的，绝对递增，不会重复
        return redisTemplate.opsForValue().increment(SEQ_KEY);
    }
}

```

**TradeService.java (改造后)**

```java
public void placeOrder(...) {
    // 1. 业务校验...
    
    // 2. 🔥 定序 (获取身份证)
    long sequenceId = sequencerService.nextId();
    
    // 3. 封装事件
    OrderEnt order = new OrderEnt();
    order.setId(sequenceId); // 此时 orderId = sequenceId
    // ...
    
    // 4. 发送给 Disruptor
    disruptorEngine.onOrder(order);
}

```

* **优点**：实现极其简单，天然持久化（Redis AOF）。
* **缺点**：性能受限于 Redis 网络 RTT（大约 1ms），并发量高时是瓶颈。

### 3. 实现方案 B：单线程内存定序 + Journal (生产级 / LMAX 模式)

这是纳斯达克、币安等头部交易所的所谓“高性能”做法。

**原理**：

1. **单线程**：一个独立的线程专门负责发号，没有任何锁竞争，纯内存操作（纳秒级）。
2. **Journal (预写日志)**：在发号的同时，将请求追加写入磁盘文件（顺序写，极快），防止断电数据丢失。

#### 代码实现 (MemorySequencer)

我们需要一个独立的组件，不依赖 Redis。

```java
@Component
public class MemorySequencer {

    // 内存计数器 (AtomicLong 或 long 均可，因为我们将在单线程中运行)

    // 模拟的 Journal Writer (实际应使用 MappedByteBuffer 顺序写文件)

    @PostConstruct
    public void init() {
        // 1. 系统启动时，读取 Journal 文件的最后一行，恢复 counter
        // long lastId = loadFromDisk();
        // counter.set(lastId);
        System.out.println(">>> 定序器已启动，当前序号: " + counter.get());
    }

    /**
     * 获取下一个序号 (线程安全版)
     */
    public long nextId() {
        long id = counter.incrementAndGet();

        // 必须先写盘，再返回 ID。如果写盘失败，系统必须 Halt。
        // 为了性能，通常会攒批刷盘 (Batch Flush)，比如每 1ms 刷一次
        writeToJournal(id); 
        
        return id;
```

### 4. 进阶：如何利用定序做高可用 (HA)？

有了 Sequence ID，你就可以做**主备复制**了。

**架构流程**：

1. **Sequencer (定序器)**：
* 收到订单请求。
* 分配 ID = 100.
* 将消息 `{id:100, type:ORDER, data:...}` **广播** 出去。


2. **Engine A (主机)**：
* 监听广播。
* 收到 ID=100。
* **处理业务** (撮合、改余额)。
* 发送成交结果给用户。


3. **Engine B (备机)**：
* 监听广播。
* 收到 ID=100。
* **处理业务** (纯内存运算，保持状态与主机一致)。
* **静默** (不发短信，不发推送，只是默默地跟单)。


4. **故障切换 (Failover)**：
* 如果 **Engine A** 爆炸了。
* 网关检测到心跳丢失。
* 网关把流量切给 **Engine B**。
* 因为 B 一直在跟单，内存状态与 A 完全一致，用户**无感**。

**修改 `DisruptorEngine.java**`:
```java
public void onOrder(OrderEnt order) {
    long sequence = ringBuffer.next(); // <--- 这就是天然的 Sequence ID
    try {
        OrderEvent event = ringBuffer.get(sequence);
        order.setId(sequence); // 🔥 强行把 RingBuffer 的序号赋给订单
        event.setOrder(order);
    } finally {
        ringBuffer.publish(sequence);
    }
}

```

* **入门**：用 MyBatis Plus 默认的雪花算法 ID 即可，足够唯一。
* **进阶**：用 Redis `INCR`。
* **硬核**：直接使用 Disruptor 的 `sequence` 作为订单 ID。这是最快、最直接的方式（因为你的撮合引擎本来就是单线程的，Disruptor 的 sequence 就是那个绝对真理）。
